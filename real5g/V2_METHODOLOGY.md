# Методика пересмотренного эксперимента free5GC + UERANSIM

Этот эксперимент заменяет исходную постановку после методологического разбора. Цель новой версии — отделить ценность активного контроля бизнес-пути от тривиального измерения сетевой задержки, сравнить ML с простыми правилами и оценивать качество на независимых запусках стенда.

## 1. Нет тавтологии «netem -> latency probe»

Основные сценарии нарушения больше не создаются `tc netem` для всего сетевого пространства NF. Для AUSF, UDM и UDR в NRF регистрируется контролируемый HTTP/2 reverse proxy. Сам контейнер NF продолжает работать штатно.

Прокси различает:
- корневой endpoint `/`, используемый blackbox-мониторингом;
- реальные не-корневые SBI-запросы бизнес-пути.

Выборочная задержка, jitter и HTTP 503 применяются только к SBI бизнес-запросам. Корневой endpoint намеренно не модифицируется. Поэтому обычная endpoint-проба может оставаться зелёной, когда регистрация UE деградирует.

Активная контрольная транзакция — реальная регистрация отдельного UERANSIM UE через NGAP/NAS/5G-AKA и последующие SBI-вызовы. Измеряется не ping и не TCP connect, а полный контрольный бизнес-путь.

## 2. Простые базовые методы

В анализ включены:
- `RootProbeZ`: робастная z-оценка задержки корневой endpoint-пробы, фиксированный порог 3.5;
- `BlackboxSLO`: Prometheus blackbox_exporter v0.28.0, порог по штатным данным;
- `BusinessLatencyZ`: робастная z-оценка задержки бизнес-пути контрольной транзакции и явный учёт 5xx;
- `BusinessSLO`: простой SLO-порог на том же бизнес-признаке;
- `UERegistrationSLO`: порог времени регистрации контрольного UE;
- `WorkloadRegistrationSLO`: порог времени регистрации обычных UE;
- `CombinedRules`: логическое объединение BusinessSLO, BlackboxSLO и UERegistrationSLO;
- `AlwaysAnomaly`: заведомо примитивный классификатор для демонстрации зависимости обычного F1 от распространённости положительного класса;
- `Passive_IF`, `PassiveZone_IF`, `Active_IF`: модели Isolation Forest для проверки добавочной ценности ML.

Если `Active_IF` не превосходит простые активные правила по заранее выбранным сбалансированным метрикам, самостоятельный вклад ML в обнаружение не заявляется.

## 3. Независимые прогоны и статистика

Эксперимент выполняется на трёх независимых GitHub-hosted runner. Каждый runner самостоятельно поднимает полный free5GC + UERANSIM стенд и содержит все типы штатных и аномальных событий в случайно перемешанном порядке.

Оценивание — leave-one-runner-out:
1. два runner используются только для штатного обучения/калибровки;
2. третий runner целиком является тестовым;
3. процедура повторяется три раза.

Таким образом случайные seed модели не подменяют независимость данных.

Основные бинарные метрики:
- balanced accuracy;
- Matthews correlation coefficient (MCC);
- sensitivity;
- specificity;
- FPR;
- macro-F1.

ROC-AUC, PR-AUC и positive-class F1 сохраняются как дополнительные показатели, но не являются единственным основанием выводов.

95%-ные интервалы строятся иерархическим bootstrap: сначала с возвращением выбираются runner-реплики, затем события внутри классов выбранного runner. Для сравнения Active_IF с базовыми методами используется парный иерархический bootstrap по одним и тем же событиям.

## 4. Баланс классов и штатная нагрузка

Каждая runner-реплика содержит штатные события нескольких типов:
- обычная регистрация одного UE;
- легитимный всплеск из 3 UE;
- легитимная повышенная нагрузка из 5 UE;
- дополнительные распределённые по времени штатные события на нагрузках 1/3/5 UE.

Аномальные сценарии также присутствуют в каждом runner. За счёт этого тест не состоит примерно на 90% из аномалий, а `AlwaysAnomaly` показывает ожидаемую сбалансированную точность 0.5.

## 5. Локализация

Основная задача локализации ограничена теми NF, для которых сформированы сопоставимые выборочные бизнес-воздействия: AUSF, UDM, UDR. Случайный Top-1 уровень равен 1/3.

Для ML-локализации используется отдельная one-class модель на каждую NF. Идентификатор NF в признаки не входит. Перед сравнением score каждой NF нормируется относительно штатного score-распределения этой же NF.

Для простых методов локализация выполняется через argmax соответствующей робастной оценки задержки/состояния. Отдельно считаются Top-1, Top-2 и MRR.

Сценарии шторма и полный отказ не скрываются внутри общей средней: результаты по каждому семейству сценариев сохраняются отдельно.

## 6. Зональные признаки

Сырые значения CPU, количества запросов и иных характеристик разных NF напрямую между собой не сравниваются.

В каждом внешнем fold сначала для каждой NF и каждого пассивного признака отдельно оценивается собственная штатная медиана и масштаб:

`scale = max(1.4826*MAD, IQR/1.349, epsilon)`

где

`epsilon = max(1e-6, 0.01*max(|median|, 1))`.

Робастная z-оценка ограничивается диапазоном [-8, 8]. Только после такой нормировки вычисляется остаток относительно соседних функций на графе пути регистрации:

`AMF -- AUSF -- UDM -- UDR`.

Это устраняет сравнение абсолютной нагрузки разнородных NF и проблему деления на практически нулевой MAD.

## 7. Проверка уклонения от контроля

Помимо обычных выборочных нарушений включён adversarial upper-bound сценарий. В нём нарушитель считается способным распознать окно контрольной транзакции и на это время полностью отключает манипуляцию, после чего возобновляет задержку для обычного UE.

Этот сценарий предназначен не для повышения метрик, а для ограничения тезиса о независимости активного контроля. Если canary распознаваем, его нельзя считать независимым наблюдением.

## 8. Защищённый SBI

Используемый pinned free5GC-compose работает с h2c/HTTP SBI. Внутренний proxy прозрачно передаёт HTTP-заголовки, поэтому токены/служебные заголовки не отбрасываются. Однако полноценное mTLS termination/service mesh в данном GitHub Actions стенде не моделируется.

В эксплуатационной архитектуре контрольная UE-транзакция не требует внешнего неаутентифицированного доступа к NF: она инициируется через штатный радиодоступ и проходит штатный бизнес-путь. Blackbox root probe используется только как сравнительный инфраструктурный baseline.

mTLS/service-mesh конфигурация остаётся отдельным этапом production validation и явно не включается в доказанную область применимости.

## 9. Дрейф

В каждую независимую реплику добавлены 24 штатных события на нагрузках 1/3/5 UE. Между ними вводятся временные интервалы; события перемешаны с основной последовательностью. Анализ сохраняет FPR по временным квартилям и уровням нагрузки.

Такой тест проверяет кратко- и среднесрочную стабильность внутри CI-сессии, но не заменяет суточный, недельный или сезонный дрейф операторской сети. Последний сохраняется как ограничение исследования.
